# Caja Diaria — memoria del proyecto

App web para **control de caja diaria** de comercios (kioscos, locales, freelancers): registrar
ingresos/egresos por día, ver saldo en vivo, arqueo, préstamos entre empresas, exportar y respaldar.
Idioma: **español rioplatense** (voseo: "registrá", "cerrá", "probá").

## Modelo de datos (claves de localStorage)

- **Contextos** (empresa/proyecto): `caja_contexts_v1` → `[{id, empresa, proyecto}]`. Default: `{id:'default', empresa:'Mi Empresa', proyecto:'Principal'}`.
- Contexto/moneda activos: `caja_active_context_v1`, `caja_active_currency_v1` (`ARS`|`USD`).
- **Días por caja:** `caja_user_days_v2::<ctxId>::<CUR>` → array de días `{iso,date,wd,si,sf,ing,egr,dif,fis,caja:[números],chq,credSi,cred,credAdj,credMovs:[{imp,note}],movs:[{imp,cpt,ref}], src:'user', ...}` (imp<0 = egreso). `fis` = suma de `caja` (partes del conteo físico, cargadas por separado en el editor).
- **Histórico importado (base):** `BASE_SEED` embebido en el código (solo `default`+`ARS`). No se respalda (es estático). `baseForCtx(ctxId,cur)` lo devuelve.
- **Préstamos entre empresas:** `caja_loans_v1` → `[{id,iso,from:{id,empresa,proyecto},to:{...},cur,amount,note}]`. `registerLoan()` genera egreso en origen + ingreso en destino (ref `PRESTAMO#<id>`). Ese `ref` es un id técnico — se guarda tal cual (nunca se toca: `removeLoanMovements`/`deleteLoan`/`editLoan` lo necesitan para encontrar y revertir los 2 movimientos) pero **nunca se muestra al usuario así**: `refLabel(ref)` lo traduce a "Préstamo" en todos los lugares de solo-lectura (`renderDayMovs`, `openDay`, `renderMovs`/Buscar movimientos, el `confirm()` de borrar movimiento, y las exportaciones CSV/Excel). El único lugar que sigue mostrando el valor crudo es el input de "Referencia" del editor de movimientos (`#editor input.ref`) — ahí es un campo editable de verdad, no una vista, y traducirlo ahí rompería el guardado.
- **Backup por email:** `caja_backup_email_v1`, `caja_backup_enabled_v1`, `caja_backup_last_v1`, `caja_backup_method_v1` (`google`|`emailjs`|`draft`), `caja_backup_url_v1`, `caja_ejs_public/service/template`.

## Funciones clave (todas en `app.html`)

- **Set de íconos SVG** (`ICON_SVG`/`ic(name,size)`, ~línea 632): reemplaza los emojis multicolor que el navegador renderiza con su propio glifo a color (🗑☁✉🖨💾💱🧾⚠️✈📲), que rompían la paleta controlada. `ic(name,size)` devuelve un `<svg>` inline (`viewBox="0 0 24 24"`, `stroke="currentColor"`) para usar dentro de template literals JS (`${ic('trash',14)}`); los lugares donde el emoji/ícono estaba en HTML **estático** (no generado por JS) tienen el `<svg>` pegado literal en vez de una llamada a `ic()`, porque ese HTML se parsea antes de que el `<script>` corra. Iconos disponibles: `trash`, `cloud`, `mail`, `printer`, `save`, `exchange`, `receipt`, `alert`, `send`, `phone`, `grid`, `list`, `chart`, `search`. Los símbolos Unicode monocromos (▲▼◆✎✕☑→ etc.) se dejaron como estaban — heredan `currentColor` y no necesitaban reemplazo. Si se agrega un botón/ícono nuevo que el navegador podría pintar a color (revisar en varios SO), usar este mismo patrón en vez de tipear el emoji directo.
- **Navegación en grilla de íconos** (`.catnav`, arriba de todo el contenido, antes de `#warnBanner`): pedido explícito del usuario tomando como referencia el estilo de apple.com/store (imagen de referencia) — ícono grande en una placa redondeada + etiqueta abajo, en fila, en vez de la lista vertical que antes vivía en el sidebar. Los 5 botones (Resumen/Movimientos diarios/Análisis/Buscar movimientos/Préstamos) usan `class="nav-btn catnav-btn"` — **reusan la clase `.nav-btn`** a propósito para no tocar el JS de navegación ya existente (`goToView()`, el `querySelectorAll('.nav-btn')` que wirea los clicks y togglea `.on`); `.catnav-btn` solo aporta el layout visual (columna, ícono arriba). El sidebar quedó liviano: solo logo, selector de empresa/proyecto/moneda y el pie — la sección "Panel" con la lista de botones se eliminó del HTML. En mobile la grilla se envuelve sola (`flex-wrap`) en 2-3 filas y queda siempre visible arriba del contenido (no hace falta abrir el menú hamburguesa para cambiar de vista, a diferencia de antes donde la navegación vivía en el sidebar colapsable).
- **Tipografía y espaciado "grandes y con aire"** (pedido explícito del usuario, misma referencia de apple.com/store): el título de cada vista (`.topbar h2`) pasó de 21px/600 a 32px/800 con letter-spacing negativo; los números de las tarjetas KPI (`.kpi .num`) de 25px/700 a 27px/800; `--r` (radio de borde) de 10px a 14px; más padding en `.wrap`/`.kpi`/`.panel`. **Ojo con el ancho mínimo de columna de `.kpis`** (`grid-template-columns:repeat(auto-fit,minmax(230px,1fr))`): con números grandes en `Roboto Mono` bold, una columna angosta hace que el `$` se corte a otra línea (bug real, visto al agrandar la tipografía) — `.kpi .num` tiene `white-space:nowrap` a propósito para evitarlo; si se vuelve a tocar el tamaño de fuente de `.kpi .num`, hay que revisar que siga entrando en una sola línea a 4-5 columnas.
- **Editor de día** (`openEditor`/`saveDay`): "＋ Nuevo día". Incluye una sección **"⇄ Préstamo entre empresas"**:
  al guardar, `registerLoan()` agrega el egreso a ese día y el ingreso a la caja destino. El resumen refleja los préstamos pendientes en vivo. **Sin doble contabilidad.**
  A diferencia del modal de detalle (`#overlay`, cierra con click afuera), el overlay del editor (`#edOverlay`) **no tiene** handler de click-afuera-cierra — cargar un día/movimiento lleva rato y un click accidental fuera del panel no debe tirar todo lo tipeado (pedido explícito del usuario). Para salir están la ✕, "Cancelar" (ambos con `onclick="closeEditor()"`) o Escape (`keydown` global, sigue cerrando ambos overlays).
  El campo **Fecha** (`#f_date`) se puede editar tanto al crear un día nuevo como al editar uno existente (antes quedaba `disabled` al editar, sin motivo documentado — la lógica de guardado ya soportaba el cambio). `saveDay()` ya maneja bien el caso: detecta choque con otro día real en la fecha destino (`clash`, bloquea con error y no cierra el editor), y si no hay choque reemplaza la entrada de `userDays` en el mismo índice pero con el `iso` nuevo — `cascadeChain()` reordena y recalcula la cadena de `si`/`sf` para todos los días reales según la nueva fecha, así que mover un día no deja duplicados ni desalinea los saldos de los demás días.
- **"💱 Cambio de divisa"** (`registerExchange`, sección en el editor de día debajo de "Préstamo entre empresas"): compra/venta de dólares **dentro de la misma empresa/proyecto** — mismo patrón que un préstamo, pero entre las 2 monedas de un mismo contexto en vez de entre contextos, reutilizando `applyLoanMovement`. Campos: Tipo (Venta de divisa = doy US$ y recibo $ / Compra de divisa = doy $ y recibo US$), Importe en US$, Cotización ($/US$) — el importe en $ se calcula solo (`recalcFxPreview`). Se acumulan en `edState.fx` (lista, botón "＋ Sumar", igual que `edState.loans`) y se aplican al guardar el día (`registerExchange` por cada uno): genera un movimiento en la caja $ y otro en la caja US$ de ese mismo contexto, con concepto **"Venta de divisa"** / **"Compra de divisa"** (+ nota opcional) y `ref` fijo **"Cambio"** (sin id único: es solo una etiqueta, no se usa para buscar/revertir movimientos como sí pasa con `PRESTAMO#<id>`). `recalcEditor()` sí refleja en vivo el ingreso/egreso pendiente de estos cambios en el "Saldo final" previsualizado, según si la moneda que se está editando (`CUR`) es la que entra o la que sale en esa operación.
- **Saldo de préstamos por empresa/proyecto** (`ctxLoanNet(ctxId,cur)`): saldo neto de un contexto sumando **todas** las contrapartes (no por par) — positivo = le deben (prestó más de lo que recibió), negativo = debe. Se muestra en 2 lugares: (1) **badge en el sidebar** (`#ctxLoanBadge`/`renderCtxLoanBadge`, debajo del selector de Empresa/Proyecto) con el saldo del contexto **activo**, en cada moneda que tenga saldo pendiente — se actualiza al cambiar de empresa/proyecto (`renderCtxSelectors`) y al registrar/editar/eliminar un préstamo (`renderLoans`); (2) panel **"Resumen por empresa / proyecto"** en la vista Préstamos (`renderLoanSummary`, arriba de "Saldos entre empresas / proyectos"), que lista todas las empresas/proyectos con saldo pendiente. Convención de signo (ojo, es sutil): en `registerLoan`, quien **presta** (`from`) queda con un **egreso** y por eso **le deben**; quien **recibe** (`to`) queda con un **ingreso** y por eso **debe** — `ctxLoanNet` suma `+amount` cuando el contexto es `from` y `-amount` cuando es `to`. **Tanto el badge del sidebar como cada fila del "Resumen por empresa/proyecto" son clickeables** y abren `openLoanDetail(ctxId)`: un modal (usa `#modal`/`#overlay`, mismo patrón que `openDay`) con el desglose **por contraparte** — "▲ Le deben" (contrapartes que le deben, en verde) y "▼ Le debe a" (contrapartes a las que les debe, en rojo) + saldo neto, todo separado por moneda. El neto por contraparte lo calcula `ctxCounterpartyNets(ctxId,cur)` (net>0 = esa contraparte le debe; net<0 = el contexto le debe a esa contraparte), resolviendo el nombre actual con `ctxLabelById` (cae al label guardado en el préstamo si el contexto ya no existe).
- **Vista "Préstamos" — editar/eliminar** (`renderLoanTable`): cada fila del "Historial de préstamos" tiene iconos **✎/🗑** (`.rowact`, igual patrón que días/movimientos). `deleteLoan(id)` y `editLoan(id)` usan `removeLoanMovements(loan)` para encontrar y quitar los 2 movimientos ligados (por `ref==='PRESTAMO#'+id`, en la caja origen y destino, buscando en `caja_user_days_v2::<ctxId>::<cur>` — **no** solo en la caja activa) y recalcular ese día (`ing`/`egr`/`nmov`/`sf`/`cascadeChain`) en ambos contextos — así no quedan movimientos huérfanos. `editLoan(id)` precarga el formulario de arriba (origen/destino/moneda/importe/nota/fecha) con `editingLoanId` seteado, cambia el botón a **"✓ Guardar cambios"** y agrega un **"Cancelar edición"**; al guardar, el handler de `loanSubmit` revierte el préstamo viejo y llama `registerLoan()` de nuevo con los valores nuevos (queda con un id nuevo, no importa: el historial no depende del id para mostrarse). `deleteLoan(id)` ahora sí revierte los movimientos (antes solo borraba el registro y los dejaba huérfanos).
- **Acciones por fila** (`.rowact` ✎/🗑): en "Movimientos diarios" (días) y "Buscar movimientos" (asientos), cada fila `src:'user'` muestra editar (`editDay`) y eliminar (`deleteDay` para días, `deleteMov(iso,idx)` para un movimiento — recalcula ing/egr/sf/nmov/dif y `cascadeChain`). Los días/movimientos del histórico importado (`src:'base'`) **no** muestran iconos (read-only). Los botones usan `event.stopPropagation()` para no disparar el modal de detalle de la fila.
- **🖨 Imprimir resumen del día** (`printDay(iso)`): botón "🖨 Imprimir" en dos lugares — el panel "Movimientos del día" del Resumen (`#dayPrintBtn`, siempre visible, imprime el día activo `last`, a diferencia de Editar/Agregar que solo aparecen si `src==='user'`) y dentro del propio modal de detalle (`openDay`, junto a la ✕). `printDay()` abre/actualiza el modal con `openDay(d)` y llama `window.print()`. El CSS `@media print` oculta todo (`.app`, `.tip`, overlays cerrados) y deja solo el `.overlay.on .modal` sin sombra/fondo/bordes redondeados a ancho completo, ocultando además la ✕ y los botones `.btn-ghost` del header (Editar/Imprimir) para que no salgan en el papel. El modal ya traía saldo inicial/ingresos/egresos/saldo final + tabla de movimientos + control de caja (sistema vs. real) — se le agregó **empresa/proyecto y moneda** en el subtítulo (`ctxInfo`, antes solo tenía fecha) para que la hoja impresa sea autocontenida y no dependa de la pantalla. Funciona con cualquier día, incluido el histórico (`src:'base'`, solo lectura).
- **Resumen (v-dash) = el día**: KPIs de Saldo inicial/Ingresos del día/Egresos del día/Saldo final (`renderKpis`). Los **números grandes NO cambian** (siguen siendo `d.si`/`d.ing`/`d.egr`/`d.sf`, el cálculo de movimientos de siempre) y tienen una línea chica debajo con el desglose **"Efectivo $X · Crédito $Y"** donde **Efectivo = número grande − Crédito** (no es un dato independiente: es el número grande neto de créditos) y **Crédito** = el acumulado de créditos correspondiente (`d.credSi`/`d.cred` en Saldo inicial/final; en Ingresos/Egresos del día, la suma de los `d.credMovs` de ESE día con signo +/−). Por construcción, **Efectivo + Crédito siempre sale igual al número grande** de esa tarjeta — es la forma en que el usuario pidió verlo ("saldo final es suma de efectivo + créditos"). Una 5ª tarjeta, más chica (`.kpi.small`, pedido explícito del usuario), muestra **"⚖ Diferencia de caja"** del día activo: el `d.dif` con color verde/rojo según `isWarn(d)` (o gris + "Sin arqueo cargado" si `d.fis==null`), y debajo "Según sistema $X" / "Caja real $Y" — a diferencia de la alarma (`#warnBanner`), esta tarjeta se ve **siempre** para el día activo, tenga o no una diferencia grande, sin tener que abrir el detalle del día. + panel "Movimientos del día" (`renderDayMovs`) con la tabla de movimientos y botones **"＋ Agregar movimiento"** (alta rápida sin abrir el editor completo: `openQuickAdd`/`saveQuickMov`, panel Tipo/Concepto/Importe inline) y **"✎ Editar día"** (`editDay`) — ambos solo visibles si `last.src==='user'`.
- **Alarma de diferencia de caja** (`#warnBanner`/`renderWarnBanner`, primer hijo de `.wrap`, fuera de las `.view` — por eso queda **visible en cualquier vista**, siempre arriba de todo, sin tener que ir a buscarla a Análisis): escanea **todas** las empresas/proyectos y monedas (no solo la caja activa) con `computeGlobalWarnings()`, que recorre `contexts` × `['ARS','USD']` llamando a `ctxRealDays(ctxId,cur)` (carga esa caja con `loadUserDaysFor`+`cascadeChain`+`baseForCtx`, siempre releyendo de `localStorage` — no pisa el estado de la caja activa) y filtra con el mismo umbral que `isWarn()`. **Solo mira el ÚLTIMO día cargado de cada caja**: un descuadre viejo con días conciliados después NO dispara la alarma (pedido explícito del usuario: "solo que aparezca la del día" — la primera versión mostraba el descuadre histórico más reciente con "+N más" y le resultaba ruido). Efecto colateral asumido: registrar un préstamo/movimiento en una fecha posterior al día descuadrado también la apaga (el día del préstamo pasa a ser el último, sin `fis` → `dif=null`). Cada ítem muestra **"Según sistema" vs "Caja real" vs "Diferencia"** (mismos rótulos/valores que el modal `openDay`: `sf` = saldo según movimientos, `fis+cred` = caja física + créditos = lo contado en la realidad) — no solo el número de la diferencia, para poder comparar de un vistazo qué dice el sistema contra qué hay en la realidad (pedido del usuario). Cada ítem es clickeable (`jumpToCaja(ctxId,cur,iso)`): cambia de empresa/proyecto y moneda activa si hace falta, navega al Resumen (`goToView('dash')`, reemplaza al handler viejo de `.nav-btn`) y abre el detalle de ese día (`openDay`). Se recalcula en cada `renderAll()`, así que cualquier alta/edición de día o préstamo la mantiene al día — por eso registrar un préstamo nuevo ahora también llama `renderAll()` (antes solo `renderLoans()`, que no tocaba Análisis ni la alarma).
- **Análisis rediseñada**: arriba de todo, **"Resumen por empresa / proyecto"** (`renderCtxSummaryCards`, grilla `#ctxSummaryCards` con clase `.kpi.ctxcard`) — una tarjeta clickeable por cada contexto con su saldo $ y US$ (último día real de esa caja, vía `ctxRealDays`) + la posición neta de préstamos (`loanNetLine`, si tiene). Click en la tarjeta = `jumpToCaja(ctxId,'ARS',null)` (cambia de caja y va al Resumen). Debajo, **"Préstamos entre empresas — detalle"** (`renderAnaLoanDetail`, `#anaLoanDetail`): KPIs generales (préstamos registrados, movido en $ y US$ histórico bruto, empresas con saldo pendiente) + una tabla con Le deben/Debe/Neto por moneda y cantidad de préstamos de cada empresa/proyecto (más detallado que el badge/resumen de la vista Préstamos, que solo muestra el neto) — cada fila abre `openLoanDetail(ctxId)`. Debajo, **"Crédito vs. efectivo"** (`renderCreditCashRatio`, `#creditCashRatio`): por cada caja con al menos un arqueo cargado, compara el `fis` (caja real) contra el `cred` (créditos a cobrar) del último día con `fis!=null`, como una barra apilada azul/ámbar con el % de crédito — el ámbar es un color fijo (`#f0a020`/gradiente `#b45309→#f0a020`), **no** `var(--gold)`, porque en el tema claro de la app `--gold` está redefinido igual a `--blue` (`#1a73e8`) y usarlo hacía que las dos leyendas se vieran del mismo color. Todo lo que había antes en Análisis (KPIs de Ingresos/Egresos totales, Evolución del saldo, Composición, Diferencias de caja, Flujo mensual, Principales conceptos, Actividad por día de semana, Resumen mensual detallado) sigue existiendo tal cual, pero ahora vive **colapsado al final** dentro de un `.month`/`.mhead`/`.mbody` (reusa el mismo patrón/CSS y la función `toggleM(this)` que ya usaban los meses del índice, con `data-key="ana-old"` para que `openMonths` recuerde si quedó abierto) bajo el título "Gráficos históricos".
- **Selección con suma neta** (`.selbar`, botón `.btn.on`): botón **"☑ Seleccionar"** en el Resumen (`daySelBtn`/`toggleDaySelMode`, junto a "＋ Agregar movimiento") y en "Buscar movimientos" (`movSelBtn`/`toggleMovSelMode`). Agrega una columna de checkboxes (`.selchk`) a la tabla; tildar movimientos muestra una barra celeste con "N seleccionado(s) · Suma neta: $X" (con signo, ingresos suman/egresos restan) y un link "Limpiar selección". En Buscar movimientos la clave de cada ítem es `iso#índice` (`_movByKey`), y al filtrar la búsqueda la selección se recorta sola a lo que sigue visible. Disponible también en días de solo lectura (histórico), ya que sumar no modifica nada — a diferencia de Agregar/Editar, que siguen restringidos a `src==='user'`.
- **Arqueo del día**: "Caja real (conteo físico)" se carga **por partes** (igual patrón que créditos): el editor tiene una lista (`edState.fisMovs`, `#fisMvList`/`renderFisMovRows`/`blankFisMov`) con botón **"＋ Agregar parte del conteo"** — cada fila tiene su propio **toggle ＋/−** (pedido explícito del usuario: "que me permita sumar como el excel") además del importe, así se puede restar un faltante/diferencia dentro de la misma lista en vez de tener que cargar un número ya neteado a mano. "Total contado" se previsualiza en vivo con signo (`recalcFis`, `pesoS`, suma todas las filas aplicando +/−). Al guardar, `saveDay` arma `cajaParts` aplicando el signo de cada fila, `d.caja` = ese array (con negativos donde corresponda) y `d.fis` = su suma (o `null` si no se cargó ninguna parte). El detalle del día (`openDay`) muestra el desglose **"Desglose caja real (conteo físico)"** con un chip por parte (las negativas en rojo, `pesoS`) + Σ total. Compat: un día viejo con `fis`/`caja` como valores sueltos sin signo (de antes de este cambio) se reconstruye como fila(s) **＋** al reabrir para editar — `type` se infiere del signo del valor guardado (`v<0?'out':'in'`), nunca se pierde nada.
- **"Cheques / valores"** sigue siendo un campo único (no itemizado).
- **"Créditos a cobrar"** — es un **saldo acumulado día a día** (como la caja), no un número suelto. El editor muestra "Saldo anterior" (`d.credSi`, heredado del día previo) y una **lista de ajustes** (`edState.credMovs`, `#credMvList`/`renderCredMovRows`/`blankCredMov`) con botón **"＋ Agregar ajuste de crédito"**: cada fila tiene su propio toggle +/-, un campo de **nombre/concepto** ("de quién es", `cm.note`) e importe (igual que los movimientos de caja), así se pueden cargar **varios ajustes el mismo día** sin que uno reemplace al otro. "Nuevo saldo de créditos" se previsualiza en vivo (`recalcCredit`, suma todas las filas). Al guardar, `saveDay` arma `d.credMovs` (itemizado, con `note`) y `d.credAdj` = suma de esas filas. `cascadeChain()` (además de `si`/`sf` de la caja) encadena `credSi`/`cred` a través de todos los días reales usando `credAdj` — corre en cada `saveDay`/`deleteDay`/`deleteMov`/préstamo, y también al inicio de `recompute()` (o sea en cada render) para que quede siempre consistente sin depender de haber guardado algo. Compat: si un día quedó con el `cred` plano de una versión anterior (sin `credAdj`), se trata como el ajuste de ese día la primera vez que se recalcula la cadena — no se pierde nada.
  **Detalle de créditos protegido por clave** (pedido explícito del usuario: "que el detalle de crédito quede oculto, solo pueda verse... con clave"): en el modal de detalle del día (`openDay`), la fila "Créditos a cobrar" del Control de caja muestra el saldo (número) siempre, pero al lado tiene un botón **"🔒 Ver"** (`openCreditDetail()`) que abre el desglose por nombre/concepto **solo después de pedir una clave** (`CREDIT_PIN_KEY='caja_credit_pin_v1'`, guardada en este navegador — mismo nivel de seguridad liviano que el código de sync, no es una cuenta real). Sin clave configurada, el primer toque pide crearla (mínimo 4 caracteres); clave incorrecta solo muestra un toast, nunca abre el modal. `creditNotesBreakdown(ctxId,cur)` suma **todos** los `credMovs` de **todos los días reales** de esa caja (reusa `ctxRealDays`), agrupados por `note`, y `renderCreditDetailModal()` los muestra ordenados de mayor a menor + un total, con un link "Cambiar clave" (solo pide la clave nueva, ya que para llegar ahí adentro ya te autenticaste). El viejo panel **"Detalle de créditos del día"** que antes vivía sin protección en `openDay()` (mostraba los `note` de ESE día nada más) se **eliminó** — quedaría inconsistente tener un desglose sin proteger al lado de uno protegido con la misma información. `openCreditDetail()`/`changeCreditPin()` usan `prompt()` nativo — no hay pantalla de configuración dedicada, a propósito, para no sumar UI a algo que se usa poco.
- **Diferencia de caja = movimientos vs (caja física + créditos)**: `dif` compara "Saldo según movimientos" (`sf`) contra el **"Saldo final (caja + créditos)"** = `fis + cred` — los créditos a cobrar cuentan como efectivo para esta comparación, a pedido explícito del usuario ("para la diferencia de caja los créditos se suman al efectivo y ese es el saldo final"). `chq` (cheques) sigue siendo solo informativo, no entra en el cálculo. `cascadeChain()` es la única fuente de verdad de `dif` (lo recalcula siempre, junto con `credSi`/`cred`, para todos los días reales en cada pasada — los sitios que guardan un día calculan un `dif` provisorio con la fórmula vieja, pero `cascadeChain()` lo corrige inmediatamente después). El modal de detalle (`openDay`) muestra la línea **"Saldo final (caja + créditos)"** justo antes de "Diferencia de caja" para que se entienda de dónde sale la comparación. (Nota: este dato es independiente del desglose Efectivo/Crédito de los KPIs del Resumen, que reparte el `sf`/`si`/`ing`/`egr` de movimientos puros — ver bullet de Resumen.)
- **⬇ Excel** (`downloadExcel`): genera un `.xlsx` real multi-hoja **sin librerías** (ZIP+OOXML a mano: `zipStore`/`buildXlsx`). Hojas: Resumen diario, Movimientos, Préstamos — todas las empresas + histórico.
- **⤓ Respaldo** (`backupBtn` + `importFile`): exporta/importa el respaldo `.json` (re-importable). Formato = `fullBackupPayload()` = `{exportedAt, contexts, data:{ctxId:{ARS,USD}}, loans}`.
- **✉ Backup diario** (`openBackupSettings`): panel/modal con guía in-app. Métodos:
  - **Google Apps Script** (recomendado, sin límite de tamaño): POST `no-cors` a la URL `/exec`; el script del usuario manda el mail con el `.json` adjunto. La guía + el código están dentro del modal, generados por `appsScriptCode(email)` con los datos reales ya cargados (config de Firebase, código de sync, email) — copiar y pegar, sin que el usuario tenga que completar nada a mano. Ojo con el deploy: "Quién tiene acceso" tiene que ser **Cualquiera** — con "Solo yo" el POST se rechaza y, como es `no-cors`, la app no se entera y muestra "enviado" igual (bug real ya diagnosticado con un usuario).
    - **Por defecto** (sin configurar nada más) el envío depende de que alguien **abra la app** ese día (`maybeAutoBackup`, 1×/día, guarda la fecha en `caja_backup_last_v1` — es local a ese navegador, no viaja con la sincronización en la nube).
    - **Automático de verdad, sin depender de abrir la app** (`dailyBackup`, incluida en el mismo script generado): usa `UrlFetchApp` para autenticarse anónimo contra la Identity Toolkit REST API de Firebase y leer directo el documento de Firestore (`cajas/{codigo}`) por HTTP, sin pasar por el navegador. Requiere que el usuario agregue un **disparador de tiempo** en Apps Script (Activadores → función `dailyBackup` → diario) — la guía in-app lo explica paso a paso. Corre en el servidor de Google a la hora que elijas, todos los días, hayas abierto la app o no.
    - Para que `dailyBackup` pueda leer la nube por HTTP sin interpretar el formato tipado de Firestore, `cloudPayload()` (la sync) agrega un campo extra **`backupJson`** = `JSON.stringify(fullBackupPayload())` — una copia plana en string del mismo payload que ya se sincroniza como campos nativos. `startSync()` hace un **backfill** automático (`schedulePush()`) la primera vez que conecta a un documento que todavía no tiene `backupJson`, así los usuarios que ya tenían sync activado antes de este cambio no necesitan tocar nada para que aparezca.
    - **Troubleshooting "no me llegó el backup"** (caso real ya diagnosticado): lo primero es pedirle al usuario que abra **script.google.com → su proyecto → ⏰ Ejecuciones** y vea si hay alguna corrida de `dailyBackup` ese día. (a) Si no aparece ninguna ejecución de `dailyBackup`: el disparador de tiempo nunca se configuró, o el proyecto tiene una versión vieja del código que solo tiene `doPost` (de antes de que existiera `dailyBackup`) — hay que decirle que vuelva a copiar el código desde el modal (se regenera con `appsScriptCode()`, siempre incluye ambas funciones) y lo pegue entero, sin necesidad de volver a "Implementar" (el disparador corre siempre contra el código guardado más reciente del proyecto, no contra la versión publicada como app web). (b) Si ejecuta `dailyBackup` a mano y tira error: probablemente `backupJson` no está en el documento — se puede verificar sin acceso a la cuenta del usuario, autenticando anónimo por REST contra Identity Toolkit con el `apiKey` del `firebaseConfig` y leyendo el doc de Firestore por HTTP (`GET .../databases/(default)/documents/cajas/<codigo>`), igual que hace `dailyBackup` — si `fields.backupJson` no está, la sync nunca se conectó del lado de ese usuario. (c) Ejecutar `doPost` a mano desde el editor de Apps Script SIEMPRE tira `TypeError: Cannot read properties of undefined (reading 'postData')` — es esperable (esa función espera una petición HTTP real, no una ejecución manual) y no es el bug; para probar a mano hay que elegir `dailyBackup` en el desplegable de funciones, no `doPost`.
  - **EmailJS** (alternativo; el plan free limita el tamaño → puede fallar con respaldos grandes). No tiene versión "server-side" — depende de que se abra la app.
  - **Borrador manual** (mailto + descarga). Es el fallback si el envío automático falla.
- **☁ Nube** (`openSyncSettings`/`startSync`): **sincronización entre dispositivos** con **Firebase Firestore** real (proyecto `rk-cajadiaria-5-6`, SDK compat por CDN, auth anónima). Doc `cajas/{codigo}` = `fullBackupPayload()`. `onSnapshot` baja cambios → `applyRemote()` los escribe en localStorage y re-renderiza; un `localStorage.setItem` interceptado dispara `schedulePush()` (debounce 900ms). El eco propio se ignora por `updatedBy===deviceId()`.
  - **Auto-conexión (decisión del usuario, riesgo aceptado):** `DEFAULT_FIREBASE_CONFIG` y `DEFAULT_SYNC_CODE` quedan **embebidos en el código** (`index.html`). `ensureDefaultSync()` corre una sola vez por navegador (marca `caja_sync_autoinit_v1`) y, si no hay config/código ya guardados, los completa con los valores fijos y activa la sync sola — así **cualquier navegador que abra el sitio ya comparte la misma caja**, sin pegar nada. El `firebaseConfig` no es secreto (va en el cliente); el "código de caja" fijo SÍ implica que cualquiera que vea el código fuente (el repo es público) podría conectarse a esta caja — trade-off elegido explícitamente por el usuario a cambio de cero fricción. Si el usuario desconecta manualmente (☁ Nube → Desconectar), `caja_sync_autoinit_v1` evita que se vuelva a auto-activar solo. El panel (`openSyncSettings`, con guía in-app paso a paso: crear proyecto en console.firebase.google.com, Firestore, reglas, Authentication anónimo) permite pisar el código/config con uno propio si se quiere separar datos.
  - **El usuario ya migró su caja real a su propio proyecto de Firebase** (dejó de usar el `rk-cajadiaria-5-6` compartido por defecto): configuró un proyecto propio desde ☁ Nube → "Usar un código propio", con backup/restore vía `⤓ Respaldo` (Exportar antes de conectar el proyecto nuevo, Importar después para no perder los datos que ya tenía). Para debug futuro: **no asumir que los datos reales del usuario están en el `DEFAULT_FIREBASE_CONFIG`/`DEFAULT_SYNC_CODE` embebido** — ese sigue siendo el default de fábrica para cualquier visitante nuevo del sitio, pero ya no es la caja que usa el dueño del repo día a día. El `projectId` de Firebase queda fijo desde la creación del proyecto (no se puede renombrar, solo el "nombre" visible en la consola) — no afecta nada de la app, es solo un dato interno del `firebaseConfig`.
  - Claves: `caja_sync_cfg_v1`, `caja_sync_code_v1`, `caja_sync_enabled_v1`, `caja_device_id_v1`, `caja_sync_autoinit_v1`.
  - **Estado: verificado en producción** (Firebase real: Auth Anónimo + Reglas de Firestore + lectura/escritura/tiempo real probados end-to-end; el usuario ya conectó un dispositivo real con éxito).
- **Responsive / mobile** (`app.html`): breakpoints en `@media(max-width:1000px)` (sidebar colapsable) y `@media(max-width:760px)` (grillas de formularios). El sidebar (`.side`) es `position:fixed` con `width:280px;max-width:82vw` y un `#sideScrim` (fondo oscuro) que aparece atrás — `toggleSideMenu()`/`closeSideMenu()` manejan ambos a la vez; antes el sidebar no tenía `width` explícito y el offset `left:-260px` no lo escondía del todo (bug real, corregido). Varias secciones arman su grilla con **`style="grid-template-columns:..."` inline** (Préstamo entre empresas, Cambio de divisa, la fila Fecha/Saldo inicial/Día del editor, la fila de ajuste de crédito) — un inline style le gana a cualquier regla de la media query sin `!important`, así que esas quedan apuntadas una por una: `.loanbox .fgrid,#v-loans .fgrid`, `#credMvList .mvrow`, `#edHeadGrid` (todas forzadas a 1 columna en mobile). Las tablas anchas (`#monthTable`, `#movTable`, `#loanTable`, el detalle de movimientos del día `.mvs`, y ahora también cada tabla de mes dentro de "Movimientos diarios") están envueltas en `<div style="overflow-x:auto">` — en vez de rediseñarlas para mobile, se dejan scrollear horizontalmente dentro de su propio contenedor (mismo patrón en toda la app).
  **Auditoría mobile pedida explícitamente ("que quede como una app")**, hecha con capturas reales a 390px (no solo mirando el CSS), encontró y corrigió 3 problemas concretos:
  1. **Menú "⋯" de acciones secundarias** (`#actionsMoreBtn`/`#actionsSecondary`, dentro de `.actions`): en mobile, mostrar los 6 botones de la topbar (Backup diario/Excel/Nube/Respaldo/Instalar/Nuevo día) sueltos y apilados ocupaba media pantalla arriba de cualquier vista, antes de llegar al contenido. Ahora solo "＋ Nuevo día" (la acción principal) queda siempre visible; el resto vive dentro de `#actionsSecondary`, que en desktop es `display:contents` (fluye igual que antes, sin wrapper visual) y en mobile se convierte en un menú desplegable (`position:absolute`, se abre con `#actionsMoreBtn`, se cierra clickeando afuera, eligiendo una acción, o con Escape). **Ojo con el orden en el CSS**: la regla base `.actions-secondary{display:contents}` está textualmente *después* del bloque `@media(max-width:1000px)` en el archivo — sin `!important` en las reglas de la media query, la base la pisaba sin importar el ancho de pantalla (bug real, ya pasó una vez al implementar esto). Mismo patrón que ya usa `.menu-toggle{display:grid!important}` en esa misma media query.
  2. **Cabecera de mes cortada** (`.mhead .mstats` en el acordeón de "Movimientos diarios"): Ingresos/Egresos/Cierre en una fila no entraban en 390px y "Cierre" quedaba literalmente truncado e ilegible, sin scroll posible (a diferencia de las tablas anchas, que si tienen `overflow-x:auto`). En `@media(max-width:760px)` ahora solo se muestra "Cierre" (`.mhead .mstats div:nth-child(1),.mhead .mstats div:nth-child(2){display:none}`) — el resto del detalle sigue disponible al expandir el mes.
  3. **`font-weight:600`/`800` sin cargar**: el `<link>` de Google Fonts solo pedía pesos `400;500;700` (heredado de antes de este rediseño), pero el CSS usa `600` (55 usos, ya existía antes) y ahora también `800` (agregado en el rediseño "Apple Store" para los títulos grandes). Cuando el navegador no tiene el peso exacto disponible en la fuente cargada, cae a una tipografía serif del sistema en vez de sintetizar el bold — se notaba fuerte en los títulos grandes nuevos ("Resumen ejecutivo" se veía en una serif rara). Fix: `family=Roboto:wght@400;500;600;700;800`. **Nota para verificar en este sandbox**: Playwright bloquea la red del navegador headless acá (`ERR_CONNECTION_RESET` en las capturas), así que este fix específico no se pudo confirmar visualmente en este entorno — sí se confirmó por `curl` que `fonts.googleapis.com` responde 200 y devuelve los 5 pesos.

## Convenciones / cómo trabajar acá

- Editar el HTML directamente (no hay build). Mantener el estilo existente (voseo, tema oscuro en la app, claro en el home).
- **Verificar con Playwright** antes de dar por hecho un cambio (es una app de dinero):
  - Servir: `python3 -m http.server 8099` en la raíz del repo.
  - Node + Playwright: el módulo está en `/opt/node22/lib/node_modules` → importar con ruta absoluta
    `import pw from '/opt/node22/lib/node_modules/playwright/index.js'`. Chromium ya está instalado (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`).
  - Sembrar estado por `localStorage` con `addInitScript` antes de `goto`.
  - Para validar `.xlsx`: `pip install openpyxl` y abrirlo.

## Flujo de git / deploy

- Rama de trabajo: **`claude/web-page-artifact-n434pw`**. Base: `main`.
- Ciclo: commit → push a la rama → PR a `main` → merge → **Pages redepliega solo**.
- Si el PR anterior ya está mergeado, reiniciar la rama desde `main` (`git reset --hard origin/main`) y seguir con el cambio nuevo.
